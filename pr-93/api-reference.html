API reference ​

The three endpoints an integration calls, with request and response shapes, status codes, and curl. @chainsafe/x402-express already calls /v2/verify and /v2/settle for you (steps 5 and 6 of the payment flow); this page is for calling the facilitator directly, or for reading what the middleware sends. What each verify check means is on The facilitator.

$FACILITATOR_URL below is your facilitator's base URL. The integration panel on the merchant dashboard's API keys page shows it, and $FACILITATOR_API_KEY is a key you create on that same page (it is shown only once). Both are the names the panel's .env uses.

GET /v2/supported ​

  • URL: $FACILITATOR_URL/v2/supported
  • Auth: open — no credentials required.

Request headers ​

None required. There is no request body.

Response 200 ​

json
{
  "kinds": [
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "canton:devnet",
      "extra": {
        "asset": {
          "instrumentId": {
            "id": "Amulet",
            "admin": "DSO::1220be58c2…"
          }
        }
      }
    }
  ]
}

Fields ​

FieldMeaning
kinds[]One entry per (scheme, network) pair the deployment settles. A deployment on one Canton network returns exactly one.
schemeexact — the scheme id defined by the registered Canton scheme spec. Copy into paymentRequirements.scheme.
networkA network name: canton:mainnet, canton:testnet, canton:devnet or canton:localnet. It does not carry the synchronizer id — read it from here rather than deriving it.
extra.asset.instrumentIdThe asset to price in — { id, admin }. admin is the network's DSO party: it admins Amulet, and the facilitator checks payments against it, so configure from here rather than by hand.

curl ​

bash
curl -sS "$FACILITATOR_URL/v2/supported"

POST /v2/verify ​

  • URL: $FACILITATOR_URL/v2/verify
  • Auth: your API key, as Authorization: Bearer. A missing or unknown key answers 401, and so does a key whose project has no payout party yet.
  • Rate limited: over the limit answers 429 with a Retry-After header.

What it does ​

Runs the checks settle runs before it reserves the nonce, and writes nothing to the ledger. It is an optional dry run: /v2/settle re-verifies from scratch, so calling verify first buys you a clean rejection before you commit, not a guarantee.

Request headers ​

HeaderRule
Content-Type: application/jsonRequired — any other type leaves the body unparsed and answers 400.
Authorization: Bearer <key>Required — an API key created in the merchant dashboard. A bare key with no Bearer prefix is also accepted, for clients that omit the scheme.
X-Request-IdOptional; echoed back on the response, otherwise one is minted.

Request body ​

json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "scheme": "exact",
    "network": "canton:devnet",
    "payload": {
      "payer": "buyer::1220…",
      "preparedTransaction": "<base64 blob from interactive-submission/prepare>",
      "preparedTxHash": "<lower-case hex of the 32-byte hash that was signed>",
      "signature": "<base64 Ed25519 signature over preparedTxHash>",
      "requirementsHash": "<sha256 of the canonical paymentRequirements>",
      "publicKey": "<base64 32-byte Ed25519 public key>",
      "hashingSchemeVersion": "HASHING_SCHEME_VERSION_V2"
    }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "canton:devnet",
    "amount": "500000000",
    "asset": "CC",
    "extra": { "instrumentId": { "id": "Amulet", "admin": "DSO::1220be58c2…" } },
    "payTo": "merchant::1220…",
    "resource": "https://api.example.com/paid",
    "description": "Access to /paid",
    "nonce": "3f1c…",
    "validBefore": "2026-08-14T13:05:00.000Z"
  }
}

Body fields ​

FieldRule
x402VersionMust be exactly 2, at the top level and inside paymentPayload.
paymentPayload.payloadThe seven fields above, all required except hashingSchemeVersion, which means HASHING_SCHEME_VERSION_V2 when absent. signature is canonical base64 of the 64-byte signature and preparedTxHash is 64 lower-case hex digits; any other encoding is bad_signature. publicKey replaced the older keyFingerprint — the facilitator derives the fingerprint from the key and matches it against the payer party's :: suffix.
requirementsHashSHA-256 of the RFC 8785 canonicalization of paymentRequirements; it must match the requirements sent alongside it. The signature itself covers the prepared transaction, whose sender, receiver, instrument and amount the facilitator checks against paymentRequirements.
amountInteger string of atomic units — 1 CC = 1e10, so "500000000" is 0.05 CC. Exact, not a floor: the transfer must move this amount, and an overpayment is rejected.
payToMust be a party your API key owns. Otherwise verify answers transfer_mismatch and settle answers unauthorized.
resourceRequired — the URL being paid for.
nonce, validBeforeRequired and non-empty; validBefore is ISO 8601 and settle refuses a quote past it.
assetA symbol — "CC" for Canton Coin, or a registry token's own. The instrument it names is extra.instrumentId.
extra.instrumentIdRequired {admin, id}: asset alone cannot say which registry issued the instrument, and the facilitator binds the transfer against this.
description, maxTimeoutSecondsOptional.

Response 200 — accepted ​

json
{ "isValid": true, "payer": "buyer::1220…" }

Response 200 — rejected ​

json
{
  "isValid": false,
  "invalidReason": "transfer_mismatch",
  "payer": "buyer::1220…",
  "extensions": { "detail": "amount" }
}

invalidReason values ​

scheme_mismatch, network_mismatch, requirements_expired, requirements_hash_mismatch, bad_fingerprint, bad_signature, nonce_replayed, missing_public_key, transfer_mismatch, internal_error

A body that is not a well-formed request answers 400 with invalidReason: "bad_request", and an unexpected fault answers 500 with internal_error.

POST /v2/settle ​

  • URL: $FACILITATOR_URL/v2/settle
  • Auth: your API key, as Authorization: Bearer. A missing or unknown key answers 401, and so does a key whose project has no payout party yet.
  • Rate limited: over the limit answers 429 with a Retry-After header.

What it does ​

Re-runs verify, reserves the nonce so a concurrent replay cannot spend it, and submits the payer-signed transaction to Canton. Returns the on-ledger update id.

Request headers ​

HeaderRule
Content-Type: application/jsonRequired — any other type leaves the body unparsed and answers 400.
Authorization: Bearer <key>Required — an API key created in the merchant dashboard. A bare key with no Bearer prefix is also accepted, for clients that omit the scheme.
X-Request-IdOptional; echoed back on the response, otherwise one is minted.

Request body ​

json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "scheme": "exact",
    "network": "canton:devnet",
    "payload": {
      "payer": "buyer::1220…",
      "preparedTransaction": "<base64 blob from interactive-submission/prepare>",
      "preparedTxHash": "<lower-case hex of the 32-byte hash that was signed>",
      "signature": "<base64 Ed25519 signature over preparedTxHash>",
      "requirementsHash": "<sha256 of the canonical paymentRequirements>",
      "publicKey": "<base64 32-byte Ed25519 public key>",
      "hashingSchemeVersion": "HASHING_SCHEME_VERSION_V2"
    }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "canton:devnet",
    "amount": "500000000",
    "asset": "CC",
    "extra": { "instrumentId": { "id": "Amulet", "admin": "DSO::1220be58c2…" } },
    "payTo": "merchant::1220…",
    "resource": "https://api.example.com/paid",
    "description": "Access to /paid",
    "nonce": "3f1c…",
    "validBefore": "2026-08-14T13:05:00.000Z"
  }
}

Response 200 — settled ​

transaction is the Canton update id.

json
{
  "success": true,
  "network": "canton:devnet",
  "transaction": "1220a3f…",
  "completionOffset": "42",
  "payer": "buyer::1220…",
  "extensions": { "settledAmount": "0.05", "nonce": "3f1c…" }
}

Response 400 — not settled ​

json
{
  "success": false,
  "errorReason": "bad_request",
  "errorDetails": "amount"
}

errorReason values ​

bad_request, unauthorized, scheme_mismatch, network_mismatch, requirements_expired, requirements_hash_mismatch, bad_fingerprint, bad_signature, nonce_replayed, execution_failed, timeout, facilitator_error

Every refusal above answers 400. An unexpected fault answers 500, and a facilitator that is temporarily out of capacity answers 503 with a Retry-After header; both carry facilitator_error.

curl ​

bash
# payment.json holds the body above
curl -sS -X POST "$FACILITATOR_URL/v2/settle" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $FACILITATOR_API_KEY" \
  -d @payment.json
