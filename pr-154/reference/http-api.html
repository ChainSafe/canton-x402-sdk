Facilitator APIs ​

The three endpoints an integration calls, with request and response shapes, status codes, and curl. @chainsafe/x402-express already calls /v2/verify and /v2/settle for you (steps 5 and 6 of the payment flow); this page is for calling the facilitator directly, or for reading what the middleware sends. What each verify check means is on The facilitator.

$FACILITATOR_URL below is your facilitator's base URL — the DevNet and MainNet ones are on Networks. The integration panel on the merchant dashboard's API keys page shows it, and $FACILITATOR_API_KEY is a key you create on that same page (it is shown only once). Both are the names the panel's .env uses.

GET /v2/supported ​

  • URL: $FACILITATOR_URL/v2/supported
  • Auth: open — no credentials required.

Request headers ​

None required. There is no request body.

Response 200 ​

json
{
  "kinds": [
    {
      "x402Version": 2,
      "scheme": "exact",
      "network": "canton:devnet",
      "extra": {
        "transferMethods": ["transfer-factory"],
        "synchronizerId": "global-domain::1220be58c2…",
        "feePayer": "x402-facilitator::1220096…",
        "carriages": ["inline"],
        "instruments": [
          {
            "admin": "DSO::1220be58c2…",
            "instrumentId": { "id": "Amulet", "admin": "DSO::1220be58c2…" },
            "symbol": "CC"
          }
        ]
      }
    }
  ],
  "extensions": [],
  "signers": {
    "canton:*": ["x402-facilitator::1220096…"]
  }
}

Fields ​

FieldMeaning
kinds[]One entry per (scheme, network) pair the deployment settles. A deployment on one Canton network returns exactly one.
schemeexact — the scheme id defined by the registered Canton scheme spec. Copy into paymentRequirements.scheme.
networkA network name: canton:mainnet, canton:testnet, canton:devnet or canton:localnet. It does not carry the synchronizer id — read it from here rather than deriving it.
extra.instruments[]What the deployment settles, one entry per instrument: instrumentId as { id, admin }, the registry admin party, and a display symbol. admin is the party the facilitator checks a payment's holding against, so configure from here rather than by hand. paymentRequired() reads the admin for you when a way to pay names its asset by id.
extra.synchronizerIdThe synchronizer the deployment submits to — the id a payer prepares its transfer against.
extra.feePayerThe party that relays a payer-signed transfer and pays its traffic fee. Copy into paymentRequirements.extra.feePayer — a facilitator refuses a payment naming anyone but itself. Absent until a deployment has a party configured. paymentRequired() reads it for you, and cannot be configured with one of your own; it refuses to quote against a deployment that advertises none.
extra.transferMethods[]The asset transfer methods it speaks; transfer-factory for canton-exact.
extra.carriages[]How a prepared transaction travels. inline means it is carried in the PAYMENT-SIGNATURE header itself.
extra.*extra is Optional and scheme-defined in x402 v2 §7.3, so a deployment may add its own keys and omit any of the above. Read what you need and ignore the rest.
extensions[]The ids of the x402 extensions the facilitator implements. Always present, as x402 v2 §7.3.1 requires; empty when it implements none.
signersThe parties that sign for the facilitator, keyed by network family. canton:* lists the feePayer party, and is an empty list until a deployment has one configured. Always present, as x402 v2 §7.3.1 requires.

curl ​

bash
curl -sS "$FACILITATOR_URL/v2/supported"

POST /v2/verify ​

  • URL: $FACILITATOR_URL/v2/verify
  • Auth: your API key, as Authorization: Bearer. A missing or unknown key answers 401, and so does a key whose project has no payout party yet.
  • Rate limited: over the limit answers 429 with a Retry-After header.

What it does ​

Runs the checks settle runs before it reserves the payment, and writes nothing to the ledger. It is an optional dry run: /v2/settle re-verifies from scratch, so calling verify first buys you a clean rejection before you commit, not a guarantee.

Request headers ​

HeaderRule
Content-Type: application/jsonRequired — any other type leaves the body unparsed and answers 400.
Authorization: Bearer <key>Required — an API key created in the merchant dashboard. A bare key with no Bearer prefix is also accepted, for clients that omit the scheme.
X-Request-IdOptional; echoed back on the response, otherwise one is minted.

Request body ​

json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "accepted": { "scheme": "exact", "network": "canton:devnet", … },
    "payload": {
      "assetTransferMethod": "transfer-factory",
      "preparedTransaction": "<base64 of the gzipped transaction from interactive-submission/prepare>",
      "preparedTxHash": "<lower-case hex of the 32-byte hash that was signed>",
      "signature": "<base64 Ed25519 signature over preparedTxHash>",
      "hashingSchemeVersion": "HASHING_SCHEME_VERSION_V2"
    }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "canton:devnet",
    "amount": "500000000",
    "asset": "CC",
    "extra": {
      "assetTransferMethod": "transfer-factory",
      "synchronizerId": "global-domain::1220be58c2…",
      "feePayer": "x402-facilitator::1220096…",
      "instrumentId": { "id": "Amulet", "admin": "DSO::1220be58c2…" },
      "executeBeforeSeconds": 120
    },
    "payTo": "merchant::1220…",
    "maxTimeoutSeconds": 60
  }
}

Body fields ​

FieldRule
x402VersionMust be exactly 2, at the top level and inside paymentPayload.
paymentPayload.acceptedRequired: the accepts[] entry the payer chose, here elided — a whole PaymentRequirements, with the scheme, network, amount, asset, payTo and maxTimeoutSeconds the spec requires of one. Its scheme must be exact and its network must equal paymentRequirements.network (spec Rule 1), or the answer is unsupported_scheme / invalid_network. Its other values are not compared: the transfer is bound to paymentRequirements, which the merchant takes from it after checking it against its own terms. A body whose paymentPayload has no accepted, has one with any of those fields missing or empty or a maxTimeoutSeconds that is not a whole number of at least 1, or has scheme and network at the top level instead (the pre-spec envelope), is not a well-formed request: 400 with invalid_payload.
paymentPayload.resource, paymentPayload.extensionsOptional; null is accepted for either, and neither affects the verdict. resource is { url, description?, mimeType?, serviceName?, tags?, iconUrl? } with a non-empty url, and extensions is an object keyed by extension id. A value of another shape is a malformed body: 400 with invalid_payload.
paymentPayload.payloadThe six fields above, all required except hashingSchemeVersion, which means HASHING_SCHEME_VERSION_V2 when absent. assetTransferMethod must be "transfer-factory", as in the requirements' extra; a payload without it or with another value is invalid_exact_canton_malformed_payload. signature is canonical base64 of the 64-byte signature and preparedTxHash is 64 lower-case hex digits; an empty one is invalid_exact_canton_malformed_payload, and any other encoding is invalid_exact_canton_signature_invalid. A payload missing any of the three is invalid_exact_canton_missing_proof. preparedTransaction is base64 of exactly one gzip member with no optional header fields, at most 8 KiB compressed and 72 KiB decompressed; anything else is invalid_exact_canton_malformed_payload. The payload carries no key: the facilitator reads the sender party's signing keys from the ledger by that party id, and the signature must verify under one of them (invalid_exact_canton_signature_invalid otherwise, including when none can be resolved). The signature covers the prepared transaction, whose receiver, instrument and amount the facilitator checks against paymentRequirements: that is what binds the payload to them.
amountInteger string of atomic units — 1 CC = 1e10, so "500000000" is 0.05 CC. Exact, not a floor: the transfer must move this amount, and an overpayment is rejected.
payToMust be a party your API key owns. Otherwise both verify and settle answer invalid_exact_canton_merchant_not_registered, with destination_not_allowed as the detail.
assetA symbol — "CC" for Canton Coin, or a registry token's own. The instrument it names is extra.instrumentId.
extra.instrumentIdRequired {admin, id}: asset alone cannot say which registry issued the instrument, and the facilitator binds the transfer against this.
maxTimeoutSecondsRequired — seconds the client has to complete payment. A whole number of at least 1; 0, a negative, a fraction and Infinity are all refused.
extra.assetTransferMethodRequired, and MUST be "transfer-factory". A reserved protocol key, so any other value is refused rather than carried through as scheme data.
extra.executeBeforeSecondsRequired — seconds from request time. The client turns it into the transfer's executeBefore; verification refuses a transfer whose deadline is not still at least 5 seconds ahead (invalid_exact_canton_expired).
extra.memoOptional, UTF-8, at most 256 bytes. Binds in both directions: the transfer's x402.memo must equal it exactly, and a transfer carrying one when you quoted none is refused too — x402.memo is the scheme's key, not the payer's. Either way the refusal is invalid_exact_canton_memo_mismatch.
descriptionOptional.

Response 200 — accepted ​

json
{ "isValid": true, "payer": "buyer::1220…" }

Response 200 — rejected ​

json
{
  "isValid": false,
  "invalidReason": "invalid_exact_canton_amount_mismatch",
  "payer": "buyer::1220…",
  "extensions": { "detail": "amount" }
}

invalidReason values ​

The codes the Canton exact scheme spec defines, with the cause in extensions.detail: Error codes lists every one and what to do about it. A refusal is still a 200; only the HTTP status below says the request itself failed.

A payment that was already relayed is not verified again: it answers with what became of it, settlement_pending (with the transaction and its network in extra) or invalid_exact_canton_execute_failed.

A body that is not a well-formed request answers 400 with invalid_payload, and an unexpected fault answers 500 with unexpected_verify_error.

POST /v2/settle ​

  • URL: $FACILITATOR_URL/v2/settle
  • Auth: your API key, as Authorization: Bearer. A missing or unknown key answers 401, and so does a key whose project has no payout party yet.
  • Rate limited: over the limit answers 429 with a Retry-After header.

What it does ​

Re-runs verify, reserves the payment so a concurrent replay cannot spend it, and submits the payer-signed transaction to Canton. Returns the on-ledger update id.

Settling the same payload twice is safe: the second call never submits again. It answers invalid_exact_canton_execute_failed if the first relay was rejected, and settlement_pending otherwise, even once it has committed. See Pending payments.

Request headers ​

HeaderRule
Content-Type: application/jsonRequired — any other type leaves the body unparsed and answers 400.
Authorization: Bearer <key>Required — an API key created in the merchant dashboard. A bare key with no Bearer prefix is also accepted, for clients that omit the scheme.
X-Request-IdOptional; echoed back on the response, otherwise one is minted.

Response 200 — settled ​

transaction is the Canton update id. amount is what was settled, in atomic units like the requirements' amount.

json
{
  "success": true,
  "network": "canton:devnet",
  "transaction": "1220a3f…",
  "payer": "buyer::1220…",
  "amount": "500000000"
}

Response 200 — pending ​

The transaction was relayed but its outcome is not known yet. This is not a failure: do not ask the payer for a new payment. A retry with the same payload tells you if it failed; see Pending payments. There is no update id until the transaction commits, so transaction is its preparedTxHash.

json
{
  "success": false,
  "errorReason": "settlement_pending",
  "transaction": "7c1e9a…",
  "network": "canton:devnet",
  "payer": "buyer::1220…"
}

Response 200 — the relay's other outcomes ​

The relay's other outcomes also answer 200, so a client reads the body: invalid_exact_canton_execute_failed when the ledger rejected the transaction, and unexpected_settle_error when the facilitator failed to relay it.

Response 400 — refused ​

A payment refused before anything was relayed: any verify refusal, or a malformed body (invalid_payload). A refusal always carries transaction and network, as x402 v2 §5.3.2 requires; transaction is empty, since nothing reached the ledger.

json
{
  "success": false,
  "errorReason": "invalid_exact_canton_amount_mismatch",
  "transaction": "",
  "network": "canton:devnet",
  "extensions": { "detail": "amount" }
}

Other statuses ​

StatusWhen
401No API key, an unknown one, or one whose project has no payout party yet.
429Over the rate limit; wait for Retry-After.
500A fault in the facilitator: unexpected_settle_error.
503Out of ledger capacity for the day: unexpected_settle_error with detail capacity_exhausted. Retry the same payload after Retry-After.

errorReason values ​

The same codes as verify's invalidReason, plus the settlement outcomes above: see Error codes. errorMessage, when present, is free text for logs and people; match on errorReason, never on it.

curl ​

bash
# payment.json holds the body above
curl -sS -X POST "$FACILITATOR_URL/v2/settle" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $FACILITATOR_API_KEY" \
  -d @payment.json
